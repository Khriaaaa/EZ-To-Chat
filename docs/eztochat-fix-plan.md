# 盲点解决方案

对着 `docs/eztochat-blind-spots.md` 的 25 条逐条给对策。每条写三件事：**改哪里、怎么改、怎么验收**。
状态标 ✅ 已落地 / 🔨 待做 / ⏸ 暂不做（说清为什么）。

原则只有一条：**宁可少做，不能静默做错**。宁可丢一次生成机会，不能把 A 的话当成 B 说的。

---

## 一、已经落地的（盲点 1/2/14/15/16/22 + 折叠）

### 1.1 消息唯一性：复合指纹 + 占位序号 ✅（盲点 1、4）

消息没有 id，唯一性只能自己拼。定稿规则：

- 指纹 = sha1(`会话|时间|说话人|内容|occ`)，occ 是「同 (会话,时间,说话人,内容) 的第几次出现」
- occ 用有状态计数器在导入/采集时算好，写进行里，不靠重放再推断
- 验收：全量导入条数与导出对账差 **0**（此前少了 722 条）

### 1.2 连发折叠：行数 ≠ 条数 ✅（盲点 2、3）

- 同会话 + 同说话人 + 文本完全一致 + 紧邻 + 间隔 ≤60 秒 → 折成一栏，`dup_count=N`，时间取第一条
- 超过 60 秒不折：那是两次独立发言，不是连发
- 渲染成 `内容 ×N` 方便读，原文一字不动
- **库里的行数是折叠后的**，任何统计/对账一律 `sum(dup_count)`，不许 `count(*)`
- 折完剩几十组「同秒同人同文本」是正常现象（中间夹了别的消息），不是缺陷

### 1.3 会话身份只认 wxid ✅（盲点 14、15、16、21）

- 库带 wxid 列；同名拆开（`朋友` ÷ `朋友（wxid_xxx）`）
- 只留个人会话：剔除 `@chatroom`（群聊 56 会话）与 `@openim`（企业微信 20 会话）
- **判断只用 wxid 后缀，不许按名字**——名字带「群」的可能是个人号
- 会话清单里 wxid 为空的行，对账时退回按名字匹配，并单独列出

验收：`tools/check_history.py` 退出码 0（总量差 0、逐会话对上、群聊/企微余量 0）。

### 1.4 采集与导入共用一套洗法 ✅

采集器收到的行与导入器都走同一套清洗：UTF-8 BOM、续行并入、`#` 注释行、`===` 分隔行、非聊天文件跳过。
后续所有新规则（见下）都在 `tools/import_wxexport.py` 改，改完同步采集侧。

## 二、采集与导入侧（盲点 5–8、10–12）🔨

### 2.1 排序：`seq` 为先（盲点 5、6）

本轮改：

- 任何读取路径（上下文拼接、界面显示、导出）先按 `seq` 再按 `ts`；**不许单独按 ts 排**
- 导入/采集完成后自动扫描「时序倒挂」并计数（如实报，不修数据）——导出确实有 1 条比前一条更晚
- 验收：对账脚本输出倒挂计数；上下文窗口内保证单调非降

### 2.2 文本归一：两边都对齐（盲点 7）

- 定一条唯一规则：**指纹一律用 `trim` 后的文本算**，库里原文保留不动
- 采集器与导入器同步引用同一条常量（写在共享模块，不接受两边各自实现）
- 现状 11 条首尾带空白的原文已保留；若今后发现指纹仍不一致，先查是不是有一边绕过了常量

### 2.3 一条消息可能含换行/制表符（盲点 8）

- 「一行 = 一条」只对消息**边界切分**成立，**内容里不得再按行/制表符拆**
- 含制表符的那张成绩表会原样保留；渲染层做多行/表格兜底展示，不得假设单行高度

### 2.4 占位符规范化：宁可标「未知」，不许编（盲点 9、10、11）

媒体与链接拿不到真内容，必须老老实实当「未知」处理，禁止喂模型前自行扩写：

| kind | 喂给模型的渲染 | 界面渲染 |
|---|---|---|
| image / voice / video | `[图片]`/`[语音]`/`[视频]`（一句原样） | 占位图标 |
| emoji | `[表情]`（表情 unicode 保留如 [捂脸]） | 原 token 渲染 |
| quote | `[回复了消息] + 自己的正文`；**标明「原句不可知」**，不猜 | 同 |
| link | 正文不可读 → `[分享了一个链接]`；**禁止使用 payload** | 界面给链接占位 |
| recall | `[撤回了一条消息（内容不可知）]`，不进对话流 | 灰字提示 |

- 链接里形如 `8 1314590 22dad…pic 0:0…` 的内部元数据（14 条）属于**数据泄漏**，
  导入/读取时改写为「未展示该内容」，不外发
- 具体改法：读取入口加一个 `render_for_ctx(text, kind)`，一个函数收口，模型看到的只有上面那张表

验收（待做）：单测覆盖「不可读链接不进 prompt」「quote 不编造原句」。

### 2.5 撤回与系统通知单列（盲点 12、13）

- `kind='recall'` 已单独标出的，读取时**默认排除**不进上下文
- `kind=text` 里混进去的撤回/系统句，用**固定正枚举**改判 kind：
  `撤回了一条消息`、`以上是打招呼的消息`、`通过了你的朋友验证请求`、`拍了拍…`、`发出了红包`、`向你转账`、`[名片]`、`[位置]`
- 改判只改 kind 不删行，脚本要输出改判计数（撤回 387、打招呼 31……）
- 验收：跑完对账脚本，「无 kind 的撤回/系统通知」为 0

### 2.6 同秒多条不同内容的顺序（盲点 5、6 补充）

- 同 (会话, 秒) 内多条不同内容：**不许按内容猜顺序**，一律按文件出现顺序（seq）
- 界面显示如果必须重排（气泡连侧），也要保留 seq 排序内侧栏的原始触达顺序

## 三、生成与产品路径（盲点 17–19、23）🔨

### 3.1 目标会话白名单（盲点 17、19）

生成建议只对「有人味」的会话开启：

- 排除：`文件传输助手`(590)、机器人会话(507)、公众号 `gh_*`、`@chatroom`、`@openim`
- 单条太少的会话（历史 < 8 条）**跳过生成**，不硬编
- 判据数据化：wxid 后缀 + 历史条数，不靠名字猜

### 3.2 历史参与上下文：少、近、准（盲点 23）

历史库只当「该会话的背景补课」，规则：

- 只取**当前活跃会话**（由实时窗口定），不扫描全库
- 只喂该会话**最近 40 条展开消息**（先按折叠渲染读，超长再截），不喂 15 万条
- 上下文里：撤回/系统通知已滤；连 `×N` 一栏一行；引用按「回复了消息（原句不可知）」呈现
- 历史**不回写** `messages.jsonl`，`watch` 不把历史当新消息（已是现状，继续遵守）

验收（都做完后）：对一个有重复设计模式的会话跑 A/B——带历史 vs 不带，看建议是否引用了历史梗。

### 3.3 建议永远是建议（横跨全清单）

- 建议只进建议流（suggestions + 面板），**自动填发间隙开关默认关** —— 已是产品底线，不动
- 生成端单次建议差异化校验：与该会话 60 秒内他方刚发过的内容重复 → 判为「复读」，重新生成

### 3.4 展示与统计分页（盲点 25）

- 面板列表单页最多 50 会话；单会话详情按需加载最近 N 条，不整卷读
- 大会话（>1 万条）不得执行全卷 python 级循环 —— 统计走 SQL

## 四、发布与非会话内容（盲点 17/18 相关 + 横向）🔨

### 4.1 对外素材一律脱敏（横向）

- 仓库 Public：真名、备注名、群名、对方昵称，**一律不出现在任何提交的文件里**
- 文档里引用形态一律用 A/B 兜名；「会话显示名 ≠ 对方昵称」这正是盲点 18，示例里更要守
- 发布前用 `grep` 套真实样本名单扫一遍项目文件，命中即拦

### 4.2 导出侧的完整性不承诺（盲点 20）

- 产品文档明确「索引条数 ≠ 文件数 ≠ 会话数」，不对外承诺「全量无缺」
- 面板侧对账只展示「已匹配 X / 待定 Y」，没有匹配上的单独列出，**不吃 silence**

### 4.3 发布前检查清单（横跨）

改动要过三道门：

1. `tools/check_history.py` 退出码 0 —— 数据层全绿
2. `tests/test_review_fixes.py` 通过 37 项 —— 逻辑层回归
3. 脱敏扫描 —— 公开面无真名、无内网痕迹

## 五、暂不做的事（明确说不）

| 暂缓项 | 为什么暂不投入 |
|---|---|
| 追加真 id / 破解消息级唯一性 | 微信导出没给，逆向.dll收益低、泄漏外形不确定，指纹方案已够稳 |
| 「导出无缺失」的全量校验 | 导出本身不完整（盲点 20），花大力气对不了账；按 4.2 只报已匹配 |
| 媒体内容还原 | 采集路线只读 UIA，不碰 DLL/注入，拿不到就明示「未知」，不尝试其他管线 |
| 群聊 | 产品定位就不做，不为它留分支代码 |
| 历史精确检索（FTS/向量） | 等历史接入生成路径后再评估，现在上检索是提前优化 |
